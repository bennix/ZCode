## 3.14.29 发布规则与待验收项

- 3.14.28 已公开，后续修复必须使用递增版本 3.14.29。根包版本是桌面构建元数据的唯一所有者；平台安装包、更新清单、GitHub Release tag 和下载入口需指向同一版本与同一最终源码提交。发布前 README 保持指向已公开版本；所有平台资产、更新清单和安装验收通过后再更新下载入口。
- Windows x64/ARM64 首次安装需从最终候选包独立验收并重复一次，以检查此前间歇性 NSIS 崩溃。Linux 两架构 DEB/RPM 需安装后打开 About 验证包管理器提示。Mac DMG 需签名、公证、装订、挂载后检查版权、更新状态和 Gatekeeper；本地 `release-artifacts` 最终只保留新版本已公证 DMG。
- 最终公开 Release 需提供七个安装包以及 Mac、Windows 更新元数据。旧版本安装资产只有在新版本公开下载与安装复验通过后清理。

- 更新元数据补传后的公开包复验 `38093690258`：Linux 四项和 Windows x64 成功；Windows ARM64 安装器在进入 App 更新检查前以 `0xC0000005` 崩溃，故 ARM64 About 尚未验收。WER 小型转储已作为该 run 的 `nsis-arm64-crash-dump` 留存。转储确认异常线程在 `System.dll` 的 `0x719f1581`（模块偏移 `0x1581`）读取地址 `0x0b212000` 时访问违规；安装器进程是 x86，运行在 Windows ARM64 上。阶段日志只有 `installer-process-started role=outer`，具体原生调用仍待符号与栈分析。不能将 x64 成功推广为 ARM64 成功，也不能宣称偶发安装崩溃已修复。
- NSIS 阶段诊断候选构建 `38094521592` 两架构成功；独立安装验收 `38095733925` 的 x64 安装、首次设置和 About 检查成功，显示 `Up to date: 3.14.28`。ARM64 再次以 `0xC0000005` 失败；日志已确认架构检查、单实例检查完成，崩溃在 `initMultiUser` 内。第二份转储再次指向 `System.dll+0x1581` 读取 `0x0b212000`。细分诊断候选构建 `38096288223` 两架构成功；独立安装验收 `38097633311` 的 x64 又复现故障，最后完整阶段是 `user-folder-query-completed`，未到 `user-folder-pointer-read-completed`，确认崩溃发生在上游 `System::Call '*$2(&w${NSIS_MAX_STRLEN} .s)'` 解引用已知文件夹返回指针。已在下一候选源码中改用 `$LocalAppData\Programs` 默认目录；新候选尚未构建和发布，不能宣称故障已修复。
- Linux DEB/RPM 的手动 About 检查原来进入不适用的 AppImage 更新器，可能持续停在“检查中”。源码现改为由 Main 明确提示包管理器/GitHub Releases 安装更新，并跳过 DEB/RPM 的启动轮询、渠道刷新和强制更新。候选构建 `38095826281` 的 x64/ARM64 均成功，两架构已安装 DEB 的 About E2E 实际显示 `For Linux DEB/RPM, check and install updates through your package manager or GitHub Releases`，首次设置与 X11/Weston 原生动作检查也通过。独立候选安装复验 `38097002257` 的两架构 DEB 首次启动和两架构 Fedora RPM 安装均成功；加强后的复验 `38097390147` 又在两架构已安装 Fedora RPM 内打开 About 并看到同一包管理器提示，四项作业全通过。修复尚未进入公开 3.14.28 安装包。
