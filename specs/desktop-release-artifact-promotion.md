# Linux 安装包发布转存

GitHub Actions 是 Linux deb/rpm 的构建与验收所有者；发布草稿只接收结论为 success、来源为本仓库 main 分支的 `Linux packages` run 所产出的安装包。转存任务从指定 run 取 `zencode-linux-arm64` 归档，检查四个文件条件：文件存在、版本为 3.14.26、扩展名为 deb/rpm、架构标记为 arm64/aarch64，然后上传至仍为草稿的 `v3.14.26`。任一条件失败即停止，草稿不公开。已上传资产以 GitHub SHA-256 和本地/CI 文件哈希核对。

事件顺序：发布者指定成功的 CI run → GitHub API 校验来源与结论 → 下载 CI artifact → 校验文件 → 上传 GitHub 草稿 → 发布者确认全平台资产齐全并公开。CI artifact 不是长期发布入口；GitHub Release 是公开软件包唯一入口。

Windows x64/arm64 同样从本仓库 main 分支结论为 success 的 `Windows package` run 转存，各架构只接受对应的 `ZenCode-3.14.26-win-<arch>.exe`；构建、首次启动和 UIA 操作全部通过后，该 run 才产生可转存 artifact。草稿公开前须同时有两个 Windows 安装器。

## 已发布 3.14.26 的同版资产刷新

Mac 已公证安装包包含 `37c795d0` 的连接故障切换修复，最初的 Windows/Linux 构建早于该提交。为使三个平台同版安装包使用同一份行为代码，重新执行 Windows/Linux 双架构打包验收，再从成功的 run 晋升资产。发布工作流接收 `run_id` 和完整的 `expected_sha`，校验来源仓库、workflow 名称、成功结论和 run 的 `head_sha`；不以分支名代替提交身份。`expected_sha` 应是包含修复的当前提交。GitHub Release 独占公开资产状态，工作流不修改构建 artifact。

刷新已发布资产的顺序：下载指定 run 的精确文件名 → 计算本地 SHA-256 → 以带本次工作流 run ID 的临时名称上传到同一 Release → 从 GitHub 资产元数据核对临时资产 SHA-256 → 将旧规范名称改成唯一备份名称 → 将临时资产改成规范名称 → 再次核对规范资产 SHA-256 → 删除备份。临时上传或哈希校验失败时不触碰旧资产；规范名称改名失败时尝试恢复备份名称并让作业失败。重复运行使用新的临时/备份名称，避免复用旧上传结果。每个架构资产独立晋升；最终必须核对七个规范资产及 GitHub 哈希，并更新发布说明与审计记录。

发布状态所有者是 GitHub Release；GitHub Actions run 只提供不可变的构建/验收证据，下载的本地副本只用于哈希核对。该流程不承诺跨多个架构资产的原子切换。任何一步失败时保留可恢复的临时或备份资产，由发布者核查，不把混合版本视为完成。发布标签必须指向与全部最终资产行为代码一致的提交；文档提交可晚于打包，不改变二进制内容。
